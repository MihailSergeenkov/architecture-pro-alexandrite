## 1. Проблемные места

### 1.1. Архитектура и интеграции

* Один инстанс для каждого приложения (Shop API, CRM API, MES API) и один инстанс для каждой БД — отсутствие горизонтального масштабирования. А также любая перезагрузка = простои, рост нагрузки = деградация производительности.
* Нет read‑реплики у PostgreSQL: MES читает большие объёмы заказов, что при росте заказов упирается в одну базу (реплику) и увеличивает время отклика.
* RabbitMQ единая точка интеграции CRM и MES без явного описания durability, DLQ, retry и мониторинга — высокие риски потери сообщений и «зависших» заказов в CRM/MES, которые навсегда остаются в PRICE_CALCULATED или MANUFACTURING_APPROVED (и тд) и никогда не доходят до следующего этапа процесса.
* Некорректное описание процесса: на схеме нет БД для CRM (БД действительно не сохраняет свое состояние?), не прорисована интеграция Shop и MES (нет понимания каким образом MES узнает о наличии заказа, далее сделаю допущение, что как-то понимает, может также через RabbitMQ).
* Слабая наблюдаемость: из описания есть ли какие-либо метрики (через Prometheus/VictoriaMetrics), логирование с корреляцией по orderId, алерты по «заказ в статусе X > N часов». Это делает диагностику задержек и потерь статусов практически невозможной.

### 1.2. Бизнес‑процесс заказов

* В MES расчёт стоимости занимает 2–3 минуты, иногда до 30 минут, при этом система продолжает линейно расти по числу заказов — без очередей/воркеров на расчёт и без явного SLA мешает масштабированию B2B‑флоу.  
* Для B2B: заказ создаётся в CRM только после сообщения из очереди от MES. При потере сообщения заказ не появляется в CRM вообще.  
* Для B2C: аналогичная проблема — если событие о смене статуса не дошло, CRM или MES «застревают» на старом статусе, клиент видит, что заказ не двигается неделями, хотя производство могло всё сделать.  

### 1.3. MES и страница операторов

* MES хранит заказы в одной БД (один инстанс), и главная страница операторов отображает последние заказы по статусам — фактически сложный агрегирующий запрос по большой таблице orders + фильтры + сортировка по времени создания. При росте объёма таблицы один индекс (если он вообще есть) и один инстанс БД не тянут запросы в acceptable latency.  
* Пагинация и фильтр по статусам на уровне UI видимо не решают проблему, если SQL‑запрос под ними остаётся тяжёлым (нет правильных индексов по статусу/дате, нет физического разделения «активные» vs «исторические» заказы) и/или не использует пагинацию с фронт системы вообще.  

### 1.4. Процессы разработки и релизы

* Только один QA, ручные E2E‑тесты и ручной деплой в release/prod, фича может попасть в прод через месяцы, проблемы с заказами накапливаются быстрее, чем правки.  
* Нет автотестов на сквозной флоу заказов (особенно B2B через API + RabbitMQ) — регрессии по статусам, потерям сообщений и неверным переходам могут не ловиться до реальных инцидентов.  
* Отсутствие canary/blue‑green: любая ошибка в очередях/обработке статусов сразу бьёт по всем заказам.  

## 2. Инициативы для устранения нежелательных ситуаций

### 2.1. Надёжность и наблюдаемость

1. Включить durability в RabbitMQ: durable‑очереди, persistent messages, DLQ и механизмы повторной обработки (retry с backoff).
2. Ввести технический SLA по статусам заказа и мониторинг:  
    - метрики по количеству заказов в каждом статусе и времени нахождения в статусе,  
    - алерты на «заказ в PRICE_CALCULATED/MANUFACTURING_STARTED/MANUFACTURING_COMPLETED > X часов/дней».  
3. Ввести корреляцию по orderId во всех логах Shop/CRM/MES + централизованный сбор логов.  
4. Добавить дэшборды по RabbitMQ: длина очередей, количество DLQ сообщений, rate публикации/чтения, ошибки обработки.

### 2.2. Поток заказов и консистентность

5. Сделать идемпотентную обработку событий и гарантированную доставку:  
    - хранить outbox‑таблицу в БД сервисов (Shop, MES, CRM) и публиковать события в RabbitMQ транзакционно (outbox pattern),  
    - на стороне консьюмера — идемпотентные операции по orderId.  
6. Ввести периодический reconciliation‑процесс (batch‑job) между CRM и MES:  
    - сравнение статусов заказов по orderId,  
    - автоисправление очевидных рассинхронов,  
    - отчёт об аномалиях (например, MES говорит SHIPPED, а CRM не ушёл дальше MANUFACTURING_STARTED).  
7. Для B2B‑API: предоставить партнёрам endpoint «проверить статус расчёта/заказа по запросу».  

### 2.3. Масштабирование и производительность

8. Горизонтально масштабировать Shop API, CRM API, MES API: поднять по несколько инстансов за балансировщиком (может быть развернуть Kubernetes).
9. Для PostgreSQL:  
    - добавить read‑репликах и перевести тяжёлые чтения на реплики,  
    - проанализировать и оптимизировать запросы по заказам (индексы по статусу, created_at, составные индексы под конкретные запросы).
10. Разделить «горячие» и «холодные» заказы:  
    - отдельная таблица или партиции для активных заказов (до CLOSED),  
    - архивирование старых заказов, чтобы запросы операторов работали по небольшой «активной» партиции.  
11. Вынести расчёт стоимости в отдельный воркер‑пул в MES:  
    - очередь задач на расчёт (можно отдельный RabbitMQ exchange/queue),  
    - несколько воркеров, масштабируемых по нагрузке.  

### 2.4. UX для операторов и API‑партнёров

12. Для MES UI операторов:  
    - специализированный API метод «последние N заказов в статусах X» с оптимизированным SQL и ограничением по количеству записей,  
    - кеширование этой выборки на 5–10 секунд, чтобы уменьшить нагрузку при частых открытиях дашборда.  
13. Добавить в MES механизмы «резервации» заказа оператором на ограниченное время, чтобы исключить гонки за новые заказы, если несколько операторов открывают страницу одновременно.  
14. Для B2B‑партнёров:  
    - понятные ошибки (429 / 503) и rate‑limits,  
    - документация по SLA расчёта цены и статусам,  
    - вебхуки/коллбеки о готовности расчёта и изменении статусов.  

### 2.5. Процессы разработки и релизы

15. Ввести автотесты по ключевым бизнес‑флоу:  
    - unit/интеграционные тесты статусов заказа на уровне каждого сервиса,  
    - минимальный набор E2E‑тестов (B2C, B2B, happy path + несколько негативных).  
16. Частичная автоматизация релизов:  
    - автоматический деплой в release с smoke‑тестами,  
    - canary‑развёртывание в проде (1 инстанс на часть трафика),  
    - feature‑toggles для рискованных изменений.  
17. Ввести SLO/SLI: latency API, доля заказов, доставленных вовремя, процент заказов с «аномальной» длительностью статуса.  

## 3. Приоритизация и целевая архитектура

### 3.1. Целевая архитектура через полгода

* Есть Observability:  
  - метрики по ключевым бизнес‑показателям (SLA по срокам изготовления, время в статусах, доля просроченных заказов, количество заказов с «зависшими» статусами),  
  - технические метрики (latency API, доля ошибок, очередь RabbitMQ, загрузка БД и воркеров),  
  - централизованные логи с корреляцией по orderId,  
  - базовый трейсинг сквозного пути заказа (Shop → CRM → MES),  
  - дэшборды и алерты, понятные как технической команде, так и бизнесу.
* Каждый сервис (Shop API, CRM API, MES API) имеет по несколько инстансов за балансировщиком (или в Kubernetes), авто‑масштабируется по CPU/RPS.
* PostgreSQL‑кластеры для Shop/CRM/MES:  
  - минимум один primary + одна read‑реплика,  
  - партиционирование/архивирование заказов,  
  - индексы под ключевые запросы.
* RabbitMQ:  
  - durable‑кластеры, persistent messages, DLQ, мониторинг,  
  - чётко отделённые очереди для расчёта стоимости, событий статусов, B2B‑интеграций.
* Поток событий между системами строится на outbox‑паттерне, все события идемпотентны, статус заказа может быть восстановлен по событиям (как бы event sourcing).  
* MES расчёт стоимости вынесен в отдельный слой воркеров, масштабируемых независимо от UI и API.  

### 3.2. Если можно реализовать только три инициативы

С учётом того, что главный бизнес‑боль — потерянные/зависшие заказы (и рост просроченных), а не просто медленный UI, я бы выбрал:

1. **Observability и метрики по заказам (инициативы 2, 3, 4, 17).**  
    - Без прозрачности невозможно понять, где именно заказы теряются или застревают, и невозможно доказать улучшения после изменений.
    - Метрики по статусам заказов, время нахождения в статусах, корреляция логов по orderId и алерты дают общую картину и для технической команды, и для бизнеса.
    - Наличие observability позволяет осознанно выбирать следующие шаги и приоритизировать инициативы по фактическому влиянию на SLA, а не по ощущениям.

2. **Надёжный поток событий и идемпотентность (инициативы 1, 5, 6).**  
    - После того как система стала измеримой, нужно устранить ключевую техническую причину потерь заказов — ненадёжный обмен событиями между Shop, CRM и MES.
    - Durable‑очереди, persistent messages, DLQ и outbox‑паттерн резко уменьшают вероятность того, что заказ «исчезнет» между системами.
    - Reconciliation‑джоба позволяет вычищать накопившиеся аномалии и не терять клиентов, пока архитектура постепенно исправляется. 

3. **Масштабирование и оптимизация MES/CRM по заказам (инициативы 8, 9, 10, 11, 12).**  
    - Это снижает время реакции для операторов и скорость расчёта цены, что напрямую уменьшает просрочки и недовольство B2B/B2C.  
    - Расчёт стоимости уходит в воркер‑пул, а дашборды операторов начинают работать на небольших горячих партициях/таблицах и, по возможности, на read‑репликах.

### 3.3. Ход рассуждений по приоритету

- Сначала необходимо реализовать Observability, потому что без этого невозможно оценить текущую ситуацию, доказать улучшения и вести предметный разговор с бизнесом на языке SLA и цифр.
- На втором шаге имеет смысл доработать надёжность потока событий, чтобы устранить основной источник потерь и рассинхронов по статусам заказов между системами.
- Третьим шагом идёт масштабирование и оптимизация производительности MES/CRM, чтобы система физически успевала обрабатывать растущий поток заказов без деградации UI и SLA.
- Уже опираясь на метрики и стабильный поток данных, можно последовательно развивать процессы разработки и релизов (автотесты, canary, feature‑flags), фокусируясь на тех участках, где это даёт наибольший измеримый эффект.
