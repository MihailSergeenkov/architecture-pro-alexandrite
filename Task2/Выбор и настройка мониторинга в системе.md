# 1. Мотивация

Мониторинг нужен, чтобы система была управляемой, где проблемы находятся до того, как на них пожалуются клиенты/сотрудники.
Это позволит:  
- вовремя замечать потерю/зависание заказов, SLA по срокам и расчёту цены, и исправлять проблемы до сообщений от B2C/B2B‑клиентов;
- понимать, где именно узкое место (RabbitMQ, бекенд сервисы, БД, расчёт цены, очередь операторов), а не просто «система стала медленной»;
- планировать мощность (CPU, память, размер БД/S3) исходя из тенденций роста заказов, а не из аварий;
- измерять эффект изменений (новый API, оптимизация запросов, масштабирование) — до/после релиза по конретным цифрам, а не по ощущениям кого-либо.

Для бизнеса это про снижение потерь контрактов, прогнозируемость сроков и аргументированное планирование инвестиций в инфраструктуру.

## 2. Выбор подхода к мониторингу

Лучше комбинировать «Четыре золотых сигнала», RED и USE по определенным зонам.
- Для API (интернет‑магазин, B2B MES API, CRM/MES): «Четыре золотых сигнала» (Latency, Traffic, Errors, Saturation), чтобы связать работоспособность сервиса с удовлетворенностью пользователя и SLA.
- Для RabbitMQ: RED (Rate, Errors, Duration) — скорость обработки, количество ошибок, задержка/длина очередей.
- Для инфраструктуры (БД, инстансы приложений (runtime)): USE (Utilization, Saturation, Errors) — загрузка ресурсов, очереди и ошибки.

## 3. Метрики и как их использовать

### 3.1. RabbitMQ

* **Number of dead-letter-exchange letters in RabbitMQ**  
    - Зачем: прямой индикатор потерянных или неуспешно обработанных сообщений → потенциально потерянных/зависших заказов.  
    - Labels: `queue`, `reason` (expired, rejected, routing_error), `message_type` (order_created, status_changed).  

* **Number of message in flight in RabbitMQ**  
    - Зачем: отражает накопление очередей — если растёт, MES/CRM не успевают обрабатывать заказы.  
    - Labels: `queue`, `message_type`.  

* Дополнительно стоит добавить:  
    - `messages_unacked` по очередям, чтобы видеть зависшие сообщения.

### 3.2. RPS и ошибки API

* **Number of requests (RPS) for internet shop/CRM/MES API**  
    - Зачем: объём трафика, тренды роста, анализ новых функциональностей.  
    - Labels: `endpoint`, `method`, `source` (web, api_partner, internal).  

* **Number of requests (RPS) per user for …**  
    - Зачем: защита от багов клиента, выявление «шумных» партнёров/API‑пользователей.  
    - Labels: `user_id` или `partner_id`.  

* **Number of HTTP 200/500 for shop/CRM/MES API**  
    - Зачем: базовый error rate; важен разброс по endpoint‑ам.  
    - Labels: `status_code` (2xx, 4xx, 5xx группами), `endpoint`, `source`.  
    - Для алертинга лучше использовать долю ошибок (`5xx / all_requests`), а не абсолютное число.

### 3.3. Латентность API

* **Response time (latency) for shop/CRM/MES API**  
    - Зачем: главный сигнал по пользовательскому опыту; нужен 95/99‑перцентиль, среднее маскирует хвосты.
    - Labels: `endpoint`, `source`, `status_class` (2xx/4xx/5xx).  

* Дополнительно: время расчёта стоимости в MES (пример названия метрики `price_calculation_duration_seconds` как histogram).  
    - Labels: `complexity_bucket` (по числу полигонов: low/medium/high), `source` (site/api_partner).  

### 3.4. Ресурсы приложений (USE)

* **CPU % for shop/CRM/MES API**  
    - Зачем: определяет, упираемся ли в CPU при пиках RPS; нужен для авто‑масштабирования.  
    - Labels: `instance_id`, `service_name`.  

* **Memory Utilisation for shop/CRM/MES API**  
    - Зачем: ловля утечек и OOM, планирование лимитов контейнеров.  
    - Labels: `instance_id`, `service_name`.  

* **Number of simultanious sessions for shop/CRM/MES API**  
    - Зачем: косвенный показатель одновременно активных пользователей и нагрузки на auth‑подсистему.  
    - Labels: `service_name`.  

* **Kb transferred/received/provided/sent for shop/CRM/MES API**  
    - Зачем: объём трафика (особенно важен для 3D‑файлов и B2B‑интеграций), планирование полосы/стоимости.  
    - Labels: `endpoint`, `source`.  

### 3.5. Базы данных и хранилища (USE)

* **Memory Utilisation for shop db instance / MES db instance (CRM db instance?)**  
    - Зачем: понимание, хватает ли памяти под рабочий set индексов/кеша, нужен для capacity planning.
    - Labels: `db_role` (primary/replica), `service_name`.  

* **Number of connections for shop db instance / MES db instance (CRM db instance?)**  
    - Зачем: защита от connection‑storm, правильно настроить пул и лимиты.  
    - Labels: `service_name`, `app_instance`.  

* **Size of shop db instance / MES db instance (CRM db instance?)**  
    - Зачем: рост данных, понимание, когда упремся в дисковую квоту/performance‑пределы и когда делать партиционирование.
    - Labels: `db_name`, `tablespace` (опционально).  

* **Size of S3 storage**  
    - Зачем: рост хранилища 3D‑файлов, расчёт стоимости и планирование политики retention.  
    - Labels: `bucket`, `file_type` (raw_model, processed_model, preview).  

### 3.6. Бизнес‑метрики

* Количество заказов в каждом статусе и время в статусе: `orders_in_status{status="PRICE_CALCULATED"}` и `order_status_duration_seconds{status="PRICE_CALCULATED"}`(histogram).
    - Зачем: видеть зависания (например, PRICE_CALCULATED или MANUFACTURING_STARTED на недели) и коррелировать со сбоями RabbitMQ/БД.
    - Labels: `status`, `channel` (b2c, b2b), `product_type` (готовое, кастомное).  

* Конверсия по B2B‑API: `api_partner_orders_created`, `api_partner_orders_failed`.  
    - Зачем: измерять, сколько заказов реально доходит до статуса SUBMITTED/PRICE_CALCULATED/MANUFACTURING_APPROVED и где ломается B2B‑флоу.  

## 4. План действий

1. **Базовая платформа мониторинга**  
    - Развернуть time‑series‑хранилище (например, Prometheus‑совместимое, можно Managed в YC) и Alertmanager.
    - Поднять Grafana и создать базовый набор дашбордов для Shop, CRM, MES, RabbitMQ и БД.  

2. **Доработка сервисов**  
    - Добавить в Shop API, CRM API, MES API экспорт метрик по формату Prometheus (RPS, latency, HTTP‑коды, размер ответов).  
    - Вынести http‑middleware/фильтры, которые автоматически считают метрики для всех endpoint‑ов.  

3. **RabbitMQ мониторинг**  
    - Включить RabbitMQ exporter, экспортировать метрики по очередям (включая DLX, messages_in_flight, messages_unacked).
    - Создать дашборд очередей статусов заказов и очередей расчёта стоимости.  

4. **Мониторинг БД и S3**  
    - Включить экспорт метрик Яндекс Managed PostgreSQL и S3 (через cloud‑мониторинг/cloud‑exporter): память, размер БД, connections, disk IOPS.
    - Сделать дашборды по нагрузке и росту данных, связать с метриками заказов.  

5. **Бизнес‑метрики заказов**  
    - Добавить в Shop/CRM/MES счётчики заказов по статусам и измерение времени нахождения в статусе (через обновление при переходе статуса).  
    - Добавить метрики по B2B‑партнёрам (количество запросов, успешных расчётов, ошибок).  

6. **Алертинг и интеграция с звонилкой**  
    - Описать SLO: процент успешных запросов B2C/B2B, медиана и 95‑й перцентиль ответа, доля заказов, выполненных в срок.  
    - Настроить алерты по SLO и по saturation (см. ниже), интегрировать с почтой, таск-трекером, мессенджером и звонилкой на критические инциденты.

7. **Конфигурация как код**  
    - Хранить все правила и дашборды в репозитории (Grafonnet), деплоить через CI/CD.

## 5. Показатели насыщенности

### 5.1. RabbitMQ

* DLX messages > 0 (по заказным очередям) дольше 5 минут.  
  - Действие: завести задачу, разобраться с причинами (ошибка в обработчике, неверный формат).  
* messages_in_flight / messages_ready растёт и держится > X (например, 10 000) более 10 минут.  
  - Действие: алерт в мессенджер: достаточно ли воркеров MES/CRM, нет ли деградации БД; при повторении — план по масштабированию воркеров и оптимизации.  

### 5.2. API и приложения

* CPU Utilization > 70–80% на инстансах API более 5–10 минут.  
  - Действие: авто‑масштабирование (если настроено) или ручное добавление инстансов по алерту в мессенджер; если в пике после маркетинговых акций — скорректировать capacity план.
* Memory Utilisation > 85–90% постоянно.  
  - Действие: завести задачу на анализ утечек/профилирование, возможное увеличение лимита/размера инстансов.  
* Error rate (5xx / all_requests) > 1% для любого критичного endpoint‑а дольше 5 минут.  
  - Действие: алерт в мессенджер, с «звонилкой» при необходимости не быстром реагировании — roll‑back релиза/отключение партнёров по rate‑limit.  
* 95‑й перцентиль latency критичных API (создание заказа, расчёт цены) > 2–3 секунд, рост по сравнению с медианой в несколько раз.  
  - Действие: алерт в мессенджер, расследование (БД, RabbitMQ, расчёт стоимости).  

### 5.3. Базы данных

* Connections > 80% лимита на primary.  
  - Действие: завести задачу на анализ пула, возможно — внедрение PgBouncer, пересмотр лимитов, добавление read‑replicas.
* Disk / DB size > 80% выделенного объёма.  
  - Действие: алерт в мессенджер: расширение диска/класса инстанса, реализация архивации и партиционирования.  

### 5.4. Бизнес‑метрики

* Количество заказов в статусе PRICE_CALCULATED или MANUFACTURING_STARTED прирастает и не уменьшается в течение суток.  
  - Действие: алерт в мессенджер, возможно — запуск reconciliation‑скриптов между CRM и MES.  
* Доля заказов, не завершённых в обещанный срок (3 недели) превышает целевое значение (например, 2–3%).  
  - Действие: сообщение в почту: пересмотр процесса, поиск узких мест.
