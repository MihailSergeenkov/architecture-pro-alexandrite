## 1. Какие системы нужно покрыть трейсингом

Трейсинг нужен вдоль всего жизненного цикла заказа: от INITIATED до CLOSED.  

Точки, где заказ может зависнуть или потеряться:  
- Интернет‑магазин (Internet Shop + Shop API):  
  - создание корзины/заказа (INITIATED → FILE_UPLOADED → SUBMITTED);  
  - загрузка 3D‑файла в S3 и запись ссылки в Shop DB.  
- MES API + MES:  
  - приёма заказа/3D‑файла от магазина;  
  - запуск и завершение расчёта стоимости (PRICE_CALCULATED);  
  - изменение статусов MANUFACTURING_STARTED/ → /SHIPPED.  
- CRM API + CRM:  
  - создание заказа в CRM (INITIATED/SUBMITTED → MANUFACTURING_APPROVED);  
  - закрытие заказа (CLOSED).  
- Messages Queue (RabbitMQ):  
  - публикация событий `order_created`, `price_calculated`, `status_changed`;  
  - обработка событий в CRM/MES (подписчики).  

Следовательно, трейсингом покрываем: Internet Shop, Shop API, CRM, CRM API, MES, MES API, фоновые джобы MES/CRM, все обработчики RabbitMQ и (хотя бы частично) ключевые запросы к БД.  Т.е. практически все системы.

## 2. Список данных, которые должны попадать в трейсинг.

Для каждого заказа нужен единый trace, сквозной через все сервисы.  

Обязательные поля (span attributes/лог‑поля):  
- `order.id` — идентификатор заказа;  
- `order.channel` — b2c/b2b;  
- `order.status_from`, `order.status_to` при каждом изменении статуса;  
- `order.customer_id` (b2c)/`partner_id` (b2b);  
- `order.price_calculation.complexity` — категория сложности 3D‑модели (по числу полигонов);  
- `order.price_calculation.duration_ms`;  
- `mq.destination` (имя exchange/queue);  
- `http.method`, `http.route`, `http.status_code`, `net.peer.ip`/`port`;  
- `db.statement` (усечённый или шаблон) для критичных операций (`insert into orders`, `update orders set status`);  
- `error` / `exception.type` / `exception.message` — для ошибок;    
- `service.name`, `service.instance.id`, `deployment.environment` (dev/release/prod).  

Обязательные спаны по пути заказа:  
- «Создание заказа» в интернет‑магазине;  
- «Загрузка 3D‑файла» (включая обращение к S3);  
- «Публикация сообщения в RabbitMQ»;  
- «Приём сообщения в MES/CRM»;  
- «Расчёт стоимости» (один большой span + child‑спаны при необходимости);  
- «Изменение статуса заказа» в каждом сервисе;  
- «Отображение заказа оператору в MES UI» (спан по HTTP‑запросу фронта к MES API);  
- «Закрытие заказа» в CRM.  

## 3. Мотивация

Зачем добавлять трейсинг и что это даст:  
- Технический эффект:  
  - сократится среднее время восстановления после сбоя — т.е. время поиска и устранения проблем по заказам, потому что можно пошагово увидеть путь заказа и место, где он остановился;
  - появится видимость латентности сквозного флоу (end‑to‑end latency: SUBMITTED → PRICE_CALCULATED → SHIPPED) и узких мест;
  - станет легче находить регрессии после релизов (сравнение распределения длительностей спанов до/после);
  - можно будет «поймать» места потери сообщений: например, trace заканчивается на публикации в RabbitMQ и не продолжается в MES/CRM.  

- Бизнес‑метрики, на которые влияет трейсинг:  
  - доля заказов, зависших в промежуточных статусах (PRICE_CALCULATED, MANUFACTURING_STARTED) — можно измерять и уменьшать;  
  - доля заказов, выполненных в срок - трейсинг покажет, какой участок цепочки чаще всего нарушает SLA;  
  - надёжность B2B‑API: отдельные метрики по трейсам запросов партнёров (от первого запроса до создания заказа в CRM).  

## 4. Предлагаемое решение

### 4.1. Технологический стек и общая схема

- Используем OpenTelemetry SDK для всех сервисов (фронты в том числе).
- Разворачиваем OpenTelemetry Collector как единый приёмник/агент.
- В качестве хранилища и UI — Jaeger.  

### 4.2. Что дорабатываем в каждом компоненте

- **Shop API (Spring Boot)**  
  - подключаем OTel SDK (HTTP server, JDBC);  
  - добавляем кастомные спаны: `order.create`, `order.file_upload`, `order.submit`, `mq.publish.order_created`.  

- **Internet Shop (Vue)**  
  - включаем фронтовый трейсинг: спаны для ключевых пользовательских действий и запросов к Shop API;  
  - связываем фронтовые trace_id с backend‑трейсами.  

- **CRM API (Spring Boot)**  
  - подключаем OTel SDK (HTTP server, JDBC);  
  - кастомные спаны `order.manufacturing_approved`, `order.closed`, `mq.consume.order_created`.  

- **MES API (C#)**  
  - подключаем OTel SDK для .NET, (HTTP server, RabbitMQ‑клиент);  
  - отдельный span `order.price_calculation`;  
  - спаны по статусам `MANUFACTURING_STARTED`, `MANUFACTURING_COMPLETED`, `PACKAGING`, `SHIPPED`.  

- **RabbitMQ**  
  - на уровне клиентов добавляем трассировку операций publish/consume: `messaging.operation = send/receive`;  

- **БД (Shop DB, MES DB)**  
  - за счёт auto‑instrumentation получаем спаны для основных SQL‑запросов;  
  - для критичных операций (insert/update orders) можно добавить именованные spans/annotations.

## 5. Компромиссы

Где трейсинг может быть малополезен или дорог:  
- Проприетарные/закрытые компоненты (например, готовый MES‑ядро без исходников), куда сложно встроить OTel SDK - там можно трейсить только «обёртки» вокруг (API, очередь), но не внутреннюю логику.  
- Очень высоконагруженные части (например, массовые batch‑операции) - полный трейсинг каждого события может быть дорог (по объёму данных); придётся включать полный трейсинг только для «проблемных» заказов.  
- S3‑хранилище от облака - детальный трейс каждого вызова может быть невозможен, ограничимся спанами на уровне приложений (вызов SDK), а не самого сервиса S3.  
- Разработка и поддержка трейсинговой инфраструктуры (Collector, backend, хранение) - это постоянные затраты; в очень маленькой компании может быть избыточно по сравнению с простым логированием.  

## 6. Аспекты безопасности

- **Аутентификация и авторизация**:  
  - доступ в UI только по корпоративным аккаунтам, роль «Поддержка», «Разработчик», «Администратор»;  
  - ограничения по действиям (кто может создавать/менять настройки, кто только читать).  
- **Ограничение ПДн**:  
  - не записывать в трейсинг номера телефонов, email, ФИО, адреса;  
  - использовать анонимные/хэшированные идентификаторы (`customer_id_hash`, `partner_id` без прямых ПДн).  
- **Сетевые ограничения**:  
  - Jaeger и Collector доступны только из внутренней сети/VPN;  
  - TLS для всех OTLP‑соединений между сервисами и Collector.
- **Хранение**:  
  - ограниченный срок хранения трейсов;  
  - резервное копирование и шифрование на диске.  
- **Аудит доступа**:  
  - логирование входов в систему трейсинга и действий администраторов.  

## 7. Автоматический мониторинг и алертинг на основе трейсинга

Необходимо сконфигурировать экспортер метрик из трейсинга (OTel Collector может агрегировать spans и отдавать metrics в Prometheus).

На основе трейс‑данных можно мониторить:  
  - распределение `order.lifecycle.duration` (SUBMITTED → CLOSED) и durations по ключевым стадиям;  
  - количество trace‑ов, обрывающихся на конкретном шаге (например, последний span — publish в RabbitMQ, но нет consume);  
  - количество ошибок/исключений в спанах типа `order.price_calculation`, `mq.consume.order_created`.  

Алерты:  
  - если доля trace‑ов, оборвавшихся на RabbitMQ (нет продолжения в MES/CRM), > X% за последние Y минут;  
  - если медиана и 95‑й перцентиль длительности `order.price_calculation` вышли за SLA;  
  - если доля trace‑ов с исключениями в обработчиках статусов > X%.
