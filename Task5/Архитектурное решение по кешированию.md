## 1. Что планируется закешировать

1. Список активных заказов для операторов — топ N заказов по статусам (SUBMITTED, PRICE_CALCULATED, MANUFACTURING_STARTED и т.д.) с фильтрами и пагинацией (самый частый запрос).
2. Результаты расчёта стоимости заказа — если партнёр повторно запрашивает расчёт для одной и той же 3D‑модели (кеш по хешу файла).
3. Справочные данные — список статусов, категории сложности изделий, параметры производства (почти статичные данные).
4. Детали заказа — при открытии карточки заказа операторами (по `order.id`).

## 2. Мотивация

MES испытывает проблемы производительности, которые влияют на операционную эффективность и удовлетворённость клиентов.

### 2.1. Проблемы

1. Медленная загрузка дашборда операторов — главная страница MES показывает список активных заказов с фильтрами по статусам, пагинацией и сортировкой по времени создания, что требует тяжёлых SQL‑запросов к единственному инстансу MES DB (PostgreSQL).
2. Рост нагрузки — линейный рост заказов (+100/месяц) увеличивает размер таблицы заказов и время выполнения запросов без индексов или партиционирования.
3. Повторяющиеся запросы — операторы часто обновляют страницу, чтобы увидеть новые заказы, каждый раз выполняя одинаковые тяжёлые запросы.
4. Нет горизонтального масштабирования БД — один primary инстанс обслуживает и чтение, и запись, что создаёт узкое место.

### 2.2. Зачем нужно кеширование

Кеширование снизит нагрузку на БД и ускорит отклик для операторов, закешировав часто запрашиваемые данные в быстром in‑memory хранилище (Redis).

## 3. Предлагаемое решение

Будем рассматривать два решения: базовое (Cache-Aside для дашборда операторов) и расширенное (Cache-Aside + Event-Driven инвалидация + Refresh-Ahead для горячих данных).


### 3.1. Решение 1: Cache-Aside с TTL‑инвалидацией

#### 3.1.1. Описание

Серверное кеширование с паттерном Cache-Aside:
- MES API проверяет Redis перед запросом к PostgreSQL.
- Если данных нет в кеше (cache miss), запрашивает БД, сохраняет результат в Redis с TTL (например, 30–60 секунд для списка заказов).
- Если данные есть (cache hit), возвращает из Redis.

Почему серверное, а не клиентское:
- Клиентское кеширование (browser cache, localStorage) не подходит для динамических данных заказов, которые меняются операторами и системой в реальном времени.
- Серверное кеширование централизует данные и обеспечивает одинаковое отображение для всех операторов.

Почему Cache-Aside: 
- Приложение контролирует, что кешировать, и не усложняет логику записи (в отличие от Write-Through).
- Кеш заполняется «лениво» только данными, которые реально запрашиваются.
- Простота реализации для read‑heavy сценариев (дашборд операторов читается чаще, чем пишется).

Почему не Write-Through:
- Write-Through синхронно пишет в кеш при каждом изменении статуса заказа, что добавляет латентность на запись и усложняет код.
- При высокой частоте изменений статусов (операторы берут/завершают заказы) кеш будет часто инвалидироваться, снижая cache hit rate.

Почему не Refresh-Ahead:
- Refresh-Ahead проактивно обновляет кеш до истечения TTL, но требует предсказания, какие данные будут запрошены.
- Для дашборда операторов сложно предсказать, какие фильтры/страницы будут нужны → высокий риск лишних запросов к БД.

#### 3.1.4. Стратегия инвалидации кеша: TTL + программная по ключу

TTL:
- Каждая запись в кеше живёт 30–60 секунд.
- Плюсы: простота, автоматическое устаревание без дополнительной логики.
- Минусы: операторы могут видеть устаревшие данные до истечения TTL (например, заказ взят другим оператором, но ещё виден в списке).

Программная инвалидация по ключу:
- При изменении статуса заказа MES API явно удаляет ключи кеша, связанные со списками заказов.
- Плюсы: снижает риск показа устаревших данных, позволяет точечно инвалидировать.
- Минусы: требует явного вызова в коде, усложняет логику записи.

Почему не Event-Driven (в данном решении):
- Event-Driven инвалидация через RabbitMQ добавляет сложность (нужен отдельный консьюмер, который слушает события и инвалидирует кеш).
- Для базового решения достаточно TTL + программная инвалидация в месте записи.

Почему не только TTL:
- TTL alone не гарантирует свежесть данных при частых изменениях.
- Комбинация TTL (защита от бесконечного роста кеша) + программная инвалидация (немедленная реакция на изменения) — оптимальный баланс.

#### 3.1.5. Плюсы решения 1

- Простота внедрения: минимальные изменения в коде MES API.
- Низкая latency для чтения: cache hit возвращает данные за <5 мс.
- Снижение нагрузки на БД: кеш поглощает 70–90% запросов списка заказов.
- TTL защищает от бесконечного роста и автоматически устаревает данные.

#### 3.1.6. Минусы решения 1

- Риск показа устаревших данных в течение TTL (30–60 секунд).
- При частых изменениях статусов программная инвалидация может сбрасывать весь кеш списков, снижая эффективность.
- Нет проактивного обновления «горячих» данных (например, топ‑10 новых заказов).

### 3.2. Решение 2: Cache-Aside + Event-Driven инвалидация + Refresh-Ahead

#### 3.2.1. Описание

Расширенное решение:  
- Event-Driven инвалидацию через RabbitMQ: при изменении статуса заказа событие публикуется, отдельный воркер в MES слушает события и инвалидирует/обновляет кеш.
- Refresh-Ahead для топ‑N новых заказов: фоновый джоб обновляет кеш списка самых новых заказов за 10–15 секунд до истечения TTL, чтобы операторы всегда видели свежие данные без задержки.

Паттерн кеширования:
- Основной: Cache-Aside (как в решении 1).
- Дополнительно: Refresh-Ahead для критичных запросов (первая страница дашборда с новыми заказами по всем статусам).

Стратегия инвалидации:
- Event-Driven: при изменении статуса/создании заказа событие триггерит обновление/инвалидацию кеша.
- TTL как fallback: если событие потеряно, TTL обеспечивает eventual consistency.

#### 3.2.4. Стратегия инвалидации: Event-Driven + TTL

Event-Driven инвалидация:
- Событие изменения статуса триггерит немедленное удаление/обновление кеша.
- Плюсы: минимальная задержка (несколько миллисекунд), высокая консистентность, операторы видят свежие данные.
- Минусы: усложнение архитектуры (нужен воркер, обработка событий, мониторинг RabbitMQ).

TTL как fallback:
- Если событие потеряно или воркер недоступен, TTL (60 сек) обеспечивает eventual consistency.
- Защита от «вечного» кеша при сбоях.

Почему не только программная инвалидация:
- Программная инвалидация в месте записи блокирует ответ пользователю до завершения операций с кешем.
- Event-Driven разгружает запись: API сразу отвечает, а инвалидация происходит асинхронно.

#### 3.2.5. Плюсы решения 2

- Минимальная задержка свежести данных: операторы видят изменения за 100–500 мс после события.
- Refresh-Ahead устраняет cache miss для критичных запросов (топ новых заказов всегда в кеше).
- Масштабируемость: воркеры инвалидации можно горизонтально масштабировать.
- Гибкость: можно выборочно применять Event-Driven для критичных данных, TTL для остальных.

#### 3.2.6. Минусы решения 2

- Сложность реализации: нужен отдельный воркер, обработка событий, мониторинг очередей.
- Зависимость от RabbitMQ: если брокер недоступен, инвалидация не работает.
- Overhead: события добавляют нагрузку на RabbitMQ.
- Refresh-Ahead может делать лишние запросы к БД, если данные не запрашиваются.

## 4. Сравнение решений

|----------|------------------------------|-------------------------------------------------------|
| **Описание** | Базовое кеширование с программной инвалидацией при записи и TTL 30–60 сек. | Расширенное с асинхронной Event-Driven инвалидацией и проактивным Refresh-Ahead для горячих данных. |
| **Плюсы** | - Простота внедрения <br>- Низкие требования к инфраструктуре<br>- Снижает нагрузку на БД<br>- TTL автоматически устаревает данные | - Высокая свежесть данных (100–500 мс после события)<br>- Refresh-Ahead устраняет задержки для критичных запросов<br>- Масштабируемость воркеров<br>- Гибкость (комбинация стратегий) |
| **Минусы** | - Риск устаревших данных до истечения TTL<br>- Частая программная инвалидация снижает cache hit rate<br>- Нет проактивного обновления | - Сложность (воркеры, события, дополнительный мониторинг)<br>-  Зависимость от RabbitMQ<br>- События добавляют нагрузку на RabbitMQ<br>- Refresh-Ahead может делать лишние запросы |
| **Время внедрения** | 1–2 недели | 3–4 недели |
| **Подходит для** | Стартовое решение, быстрое ощущение результатов, ограниченные ресурсы команды | Продакшн‑система с высокими требованиями к свежести данных и готовностью поддерживать сложность |

|-----------|--------------------------------|---------------------------------|
| **Описание** | TTL 30–60 сек + явное удаление ключей в коде при записи | События через RabbitMQ триггерят асинхронную инвалидацию, TTL как fallback |
| **Свежесть данных** | Средняя: до 60 сек устаревания | Высокая: 100–500 мс |

| **Подходит для** | Некритичные данные, read-heavy с редкими изменениями | Критичные данные, high-consistency требования, динамические изменения |

## 6. Заключение и рекомендация

### 6.1. Для стартового внедрения: Решение 1 (Cache-Aside + TTL)

Лучше начать с Решения 1, потому что:  
- Даст немедленный эффект (снижение нагрузки на БД) при минимальных затратах команды.
- Простота внедрения и поддержки, меньше точек отказа.
- Для текущей нагрузки (рост +100 заказов/месяц) TTL 30–60 сек допустим — операторы обновляют страницу вручную, и задержка в минуту не критична.

### 6.2. План перехода к Решению 2

После внедрения Решения 1 и стабилизации (1–2 месяца):  
- Добавить Event-Driven инвалидацию для списков заказов — операторы перестанут видеть устаревшие данные.
- Внедрить Refresh-Ahead для топ‑20 новых заказов — устранит задержку при первом открытии дашборда.
- Мониторинг cache hit rate, latency и консистентности данных через Grafana/Prometheus.

### 6.3. Технический стек

- Кеш: Redis (managed в Yandex Cloud или self-hosted кластер).
- Паттерн: Cache-Aside для старта, затем + Event-Driven.
- Инвалидация: TTL 30–60 сек + программная (решение 1) → TTL + Event-Driven (решение 2).
- Мониторинг: метрики cache hit/miss rate, latency, размер кеша, alarms на cache unavailable.

Такое пошаговое внедрение снизит риски, даст быструю пользу операторам и заложит основу для более сложной системы кеширования в будущем.
